# 这一轮：先写用例，再写实现

旧实现已经全部删除。这一轮只做一件事：**站在应用开发者的角度，用“理想中的 ShikiForm API”把真实业务场景写出来**，看 API 是否顺手、哪里别扭，定下来之后再写实现。

- 所有代码都是**伪代码**：`shikiform` / `shikiform/pro` 目前没有任何实现，代码不能运行，也不保证通过类型检查。
- 每个用例页 = 一个真实场景的完整 `.tsx`（源文件在仓库 `usage/` 目录，页面直接引用源文件，只有一份）。
- 代码里所有 `// ❓` 都是我拿不准的 API 点，会在每页顶部汇总；跨用例的汇总、选项和建议在 **[待拍板](/decisions/)**。
- 这些用例隐含的完整公开 API 整理在 **[API 草案](/api/)**。

## 怎么看（建议顺序）

1. **[待拍板](/decisions/)**：顶部是 2026-10-27 已拍板的 D1（删 Void / Transient / Computed 类型）、D2（树节点 pos），然后是 Q0 pos 细节与 Q1–Q10。
2. **[07 SKU 选择器](/usage/07-sku-editor/)**、**[09 查询表单 + 表格](/usage/09-query-table/)**、**[10 行展开二级表格](/usage/10-expandable-nested-table/)**：最能检验 API 的三个场景。
3. 其余用例按需翻；**[API 草案](/api/)** 当索引查。
