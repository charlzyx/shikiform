# 设计架构

ShikiForm 把「数据怎样变化」和「控件怎样显示」分开。字段值、校验和联动都交给同一个 `FormEngine`；React 负责订阅和组织字段，antd 只负责控件、布局和反馈。

如果你只想先写出一个表单，可以直接进入 [最小上手](/tutorial/1-start)，再回来理解这些边界。

## 三层分工

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| `shikiform/core` | 值与字段状态、精确 path、联动、校验、提交结果；用 `createForm` 创建引擎 | 不依赖 React 或 antd，不渲染控件 |
| `shikiform` 的 React 层 | `useForm` 保留引擎实例；`Form` 提供上下文；`Field`、结构字段和 Hooks 订阅及绑定它 | 不另建一份业务值，不替控件猜测事件参数 |
| `shikiform/antd` | 把通用绑定接到 antd 的 value/checked、事件、禁用态、反馈与布局 | 不用第二个 AntD Form store 管理同一份值 |

`shikiform/pro` 是可选的无 UI 查询逻辑层：`useQueryTable` 管理请求、分页和选择，既能接 antd，也能接原生 HTML。见 [两种查询界面](/examples#查询与校验)。

### 为什么先用通用绑定

`Field` 使用 render prop，把 `value`、`onChange(value)`、`onBlur()` 等交给你。原生 input、antd Input、自定义编辑器的事件形状不同，取值转换留在适配层。布局使用普通 React 组件，不需要增加一种布局字段。

项目可以用 `createFormHook` 预绑定自己的控件。`useAntdForm` / `useAntdField` 是现成的预绑定与匹配上下文入口，不是另一套引擎。工厂的 `useFieldContext()` 读取当前 `AppField`；通用 `useField(name)` 按路径取得绑定，两者不是同一个签名。见 [工厂参考](/reference/form-hook) 和 [antd 接线指南](/guide/antd-binding)。

## 一次输入如何流动

1. **输入**：控件把事件转换成值，调用 `field.onChange(value)`。程序写值使用 `setValue` 或 `batch`，不要直接修改 `getValue` 返回的对象。
2. **写入与联动**：引擎更新数据；`reaction` 根据读到的状态维护派生结果，`reaction.each` 处理数组行，`watch` 在显式来源变化时做动作。它们不需要等某个输入框挂载。
3. **显示**：字段绑定与 `useWatch` 订阅读到的路径/状态。控件渲染当前值、选项、错误和 pattern；父组件不必订阅每个单元格的值。
4. **校验**：默认在失焦和提交时触发。控件必须把 blur 接回绑定；也可配置 onChange。字段规则与整表 Standard Schema 在同一引擎中汇合。
5. **提交**：`submit` 等待校验，通过后才调用成功回调；结果排除 `virtual`、`display: 'none'` 和默认虚拟的计算字段。等待期间数据变更或校验被替代，会要求重试，不把未经本轮验证的新值提交出去。

联动规则的写法见 [联动](/guide/effects)，校验时序和提交失败返回见 [校验](/guide/validation)。`reaction` 是同步派生，不要把请求放进 async reaction。

## path 是位置，ID 是身份

对象里的 `profile.name`、数组里的 `items.0.price` 都是精确数据路径。`ObjectField`、数组行和树 scope 让子组件使用相对名字；effects 仍以 draft 路径访问，不另加 `../` 一类路径语言。

数组移动后，索引 path 会变化；稳定的 `rowKey` 用于保留行身份，不能拿稳定 ID 代替索引 path。树的 `pos` 是索引数组，同样会随移动变化。把操作交给 `useArrayField` / `useTreeField`，不要靠原地修改数组让 UI 猜测结构变化。

从 [数组教程](/tutorial/7-array) 开始，再看 [数组与树 Hooks](/reference/react-hooks#usearrayfield) 和 [拖动示例](/play/headless)。提交路径规则见 [path 和提交](/guide/path)。

## 显隐、编辑态与提交是不同问题

| 设置 | UI | 校验与提交 |
|---|---|---|
| `display: 'visible'` | 显示字段 | 正常校验、提交 |
| `display: 'hidden'`（包括 `$visible = false`） | `Field` 不渲染输入内容 | 仍校验，值仍提交 |
| `display: 'none'` | `Field` 不渲染输入内容 | 跳过校验，值从提交结果中排除 |
| `virtual: true` | 本身不决定显示 | 仍可校验和联动，只排除提交值 |

`pattern` 另管可编辑性：`editable`、`disabled`、`readOnly`、`readPretty`。它从父级继承，子级显式值可覆盖；阅读态怎样显示由 UI 适配层决定。禁用/只读是交互约束，不阻止程序调用写入 API。

计算字段是普通字段：`reaction` 写入 `$value` 后默认阅读态、默认虚拟。需要把派生值提交给后端时，显式设 `virtual: false`。见 [pattern](/guide/pattern)、[显隐](/guide/display) 和 [订单行](/play/orders)。

## 规则声明与组件生命周期

`Field` 的 JSX `rules` / `required` 只在该组件挂载期间有效；卸载后释放这份校验配置。仅把 display 改成 hidden 不等于卸载 `Field`，不能据此绕过校验。

表单 `fields` 声明、`registerField`、数组模板和 reaction 写入的规则不依赖输入框挂载。跨标签页仍要校验的业务规则应放在这里；只有当前页面需要的临时输入规则才放 JSX。`useField(name)` 本身是绑定 Hook，不拥有 JSX 规则生命周期。

不要让多个同 path 的组件同时提供互相竞争的 JSX 规则；需要复用输入时，把业务规则声明在表单上，由多个纯绑定消费者读取。例子见 [没挂载的字段](/guide/unmounted) 和 [标签页](/play/tabs)。
