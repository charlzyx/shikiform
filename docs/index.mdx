# 这一轮：先写用例，再写实现

旧实现已经全部删除。这一轮只做一件事：**站在应用开发者的角度，用“理想中的 ShikiForm API”把真实业务场景写出来**，看 API 是否顺手、哪里别扭，定下来之后再写实现。

想先摸手感，从 **[教程](/tutorial)** 开始。教程每一步只讲一个概念，右边可以改代码、立刻看结果。用例和 API 草案负责深度，教程不替代它们。

- 用例页仍是**伪代码**：它们会引用 `shikiform/pro`、业务自己的 UI 和接口。文档站里的教学运行时只覆盖教程用到的那部分已拍板 API，跑不了这些用例。
- 每个用例页 = 一个真实场景的完整 `.tsx`（源文件在仓库 `usage/` 目录，页面直接引用源文件，只有一份）。
- 代码里所有 `// ❓` 都是我拿不准的 API 点，会在每页顶部汇总；跨用例的汇总、选项和建议在 **[待拍板](/decisions)**。
- 这些用例隐含的完整公开 API 整理在 **[API 草案](/api)**。

## 怎么看（建议顺序）

1. **[教程](/tutorial)**：最小可运行路径。提交、失焦校验、`$visible`、pattern、`virtual`、`autorun` / `watch`、数组、Zod。
2. **[待拍板](/decisions)**：顶部是 2026-10-27 已拍板的 D1（删 Void / Transient / Computed 类型）、D2（树节点 pos）、D3–D8（effects 语法、UI Brand、pattern、表格列、删 scope、`virtual`），然后是仍开放的 Q0 / Q5 / Q10 与新的待拍板。
3. **[16 effects 参考](/usage/16-effects-reference)**：一页看完 `autorun` / `autorun.each` / `watch` + draft 代理的全部写法。
4. **[07 SKU 选择器](/usage/07-sku-editor)**、**[09 查询表单 + 表格](/usage/09-query-table)**、**[10 行展开二级表格](/usage/10-expandable-nested-table)**：最能检验 API 的三个场景。
5. 其余用例按需翻；**[API 草案](/api)** 当索引查。
6. **[案例补全清单](/coverage-checklist)**：对照 Formily / Pro / SKU 的 backlog。状态按清单，不是已经做完的 demo。
