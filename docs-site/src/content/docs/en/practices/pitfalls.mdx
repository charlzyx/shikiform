## Destructure child handles

Reassigning a local variable only changes that variable. Write through the handle to update the field.

```ts
let { $value } = d.user.name
$value = 'Ada'
```

```ts
const { name } = d.user
name.$value = 'Ada'
// Or write d.user.name.$value = 'Ada' directly.
```

### Enumerating a handle

Spread, rest and `Object.keys` enumerate a path proxy and throw in development. Pick child handles by name.

```ts
const { name, ...rest } = d.user
const copy = { ...d.user }
Object.keys(d.user)
```

```ts
const { name } = d.user
name.$value
const keys = Object.keys(d.user.$value)
```

### Destructuring an array

Use an indexed handle for a row or read the array's `$value`.

```ts
const [first] = d.items
```

```ts
const { name } = d.items[0]
name.$value
d.items.$value
reaction.each(draft.items, (row) => {
  row.name.$value
})
```

## Mutating stored values

Inside `reaction`, `watch`, and `batch`, an object or array `$value` is a writable draft. `d.user.$value.name = 'Ada'` is the path write `d.user.name.$value = 'Ada'`. `d.items.$value.push(row)` uses the same row operation as `useArrayField().push`.

```ts
d.user.$value.name = 'Ada'
d.items.$value.push(row)
```

`getValue`, `form.values`, and a validator's `value` are not that draft. In development those reads are read-only views. The view is not `===` to the stored object (it is, in production, outside an effect). `indexOf` / `includes` and `deepEqual` peel the view, so `rows.indexOf(rawRow)` still matches. Do not pass `binding().value` to a table that `push`es or `sort`s it; the error names the field path.

`structuredClone(form.values)`, `postMessage`, and IndexedDB throw `DataCloneError` on that view in development only. `snapshot(form.values)` from `@shikiform/core` is a plain copy, including omitted fields. `getSubmitValues()` is the submit payload. `toRaw(value)` is the live stored object.

A deep-frozen tree (immer / Redux) can be read. A non-configurable, non-writable child is returned raw because wrapping it would throw a proxy `TypeError`.

## Writing dynamic keys without subscribing to the whole record

`d.overrides[id].$value = price` navigates to a field and writes it. Spreading `d.overrides.$value` first reads the entire record. In a reaction, that read makes changes to other prices a dependency too. Spell indexes and keys on the draft (`d.items[i].qty`, `d.extra[key]`). `query(path)` is only for a path that is already a string, such as `query(pathOf('menus', pos)).$disabled = true` inside an effect. Outside an effect, use `form.getValue`.

```ts
watch.each(draft.rows, (row, { d }) => {
  const id = row.id.$value
  if (id) d.overrides[id].$value = row.price.$value
})
```

For each new array row, `watch.each` calls the callback once to collect reads and discards field writes; on each subsequent run it refreshes dependencies in the same pass and migrates row subscriptions when rows move, insert, or get removed. Here it records the row's ID and price. Use a field assignment for the destination in this callback. Calling `push` or mutating an object obtained from `$value` during that initial read-only pass can throw in development.

For a one-time append when a source changes, call `d.items.$value.push(row)` in the action of `watch(source, action)`. An unconditional `push` inside a `reaction` reads and changes the same array on every pass and can cause a cycle. The [dynamic fields example](/en/guide/linkage#dynamic-object-fields) shows how to derive state per object key and render the current fields.

## Reading a buffered write

`$value`, `$enum`, `$rules`, and UI state replay pending writes, so a second read in the same pass sees the new value. `d.total.$value = price * qty` then `d.tax.$value = d.total.$value * 0.1` uses that total. `d.rows.$value.push(a)` then `d.rows.$value.push(b)` appends both.

Flags (`$visible`, `$disabled`, `$readOnly`, `$omit`, `$required`) do not replay. Reading one after writing it in the same pass sees the old value and throws `ShikiUsageError` in development. Keep the new flag in a local.

## Do not mutate a Date, Map, Set, or class instance inside `$componentProps`

Those values are not plain objects, so the draft returns them raw. `date.setMonth(1)`, `map.set(key, value)`, and `box.n = 1` edit the declared instance: nothing is written and no reaction is notified. Replace the value:

```ts
d.city.$componentProps.date = new Date('2021-05-01')
const cache = d.city.$componentProps.cache as Map<string, number>
d.city.$componentProps.cache = new Map(cache).set('a', 1)
```

`structuredClone` cannot clone a draft (`DataCloneError`). Spread or `JSON.stringify` copies the plain data you read; do not pass the draft proxy to `structuredClone`.

## Repeating the scope prefix

Names inside object and row scopes are relative. Repeating the prefix creates an invalid nested path.

```tsx
<ObjectField name="address">
  <Field name="address.city" />
</ObjectField>
```

```tsx
<F.ObjectField name="address">
  {(obj) => <obj.Field name="city" decorator={[FormItem]} component={[Input]} />}
</F.ObjectField>
```

## Hiding a field and submitting it

Set `$omit` separately when hidden data should be removed from the payload.

```ts
d.taxId.$visible = false
```

```ts
d.taxId.$visible = false   // Hidden and unvalidated, still included on submit.
d.taxId.$omit = true       // Render and validate, exclude from submission.
d.taxId.$visible = false   // Together these flags skip rendering, validation and submission.
d.taxId.$omit = true
```

## Using decorator props as a value binding

A decorator's `control` supplies label and error information. Connect `value` and `onChange` with `useField` or `connect`.

```tsx
function Bad() {
  const { control } = useFieldDecorator()
  return <input {...control} />
}
```

```tsx
function NameInput() {
  const field = useField<string>()
  return (
    <input
      id={field.id}
      value={field.value ?? ''}
      onChange={(event) => field.onChange(event.target.value)}
      onBlur={field.onBlur}
    />
  )
}
```

## Computing a value in a watch

A watch skips initialization. Use a reaction to derive state from the first pass onward.

```ts
watch((d) => d.price.$value, (d) => {
  d.total.$value = d.price.$value * 2
})
```

```ts
reaction((d) => {
  d.total.$value = (d.price.$value ?? 0) * 2
})

watch((d) => d.province.$value, (d) => {
  d.city.$value = undefined
})
```

## Calling `onChange` or `form.setValue` during render

```tsx
// ✗ Mutating the form during render also writes during SSR or discarded concurrent renders
function BadInput() {
  const field = useField<string>()
  if (!field.value) field.onChange('default')
  return <input value={field.value ?? ''} onChange={(e) => field.onChange(e.target.value)} />
}
```

Never call `field.onChange` or `form.setValue` directly inside render. Server-side rendering or abandoned React renders will still execute those writes and mutate the form store. Set defaults via `initialValues` or `reaction`, and move imperative writes into event handlers or `useEffect`:

```tsx
// ✓ Write from an event handler or useEffect
function GoodInput() {
  const field = useField<string>()
  useEffect(() => {
    if (!field.value) field.onChange('default')
  }, [field.value, field.onChange])
  return <input value={field.value ?? ''} onChange={(e) => field.onChange(e.target.value)} />
}
```

## Using a reaction draft across `await` or calling `form.setValue` / `reset` / `submit` inside a `reaction`

Keep `reaction` synchronous:

- A `reaction` that returns a thenable is rejected and its draft handle expires when the pass ends. Writing through it after `await` throws `ShikiUsageError` in development and is ignored in production.
- Calling `form.setValue`, `form.reset`, or `form.submit` synchronously inside a `reaction` throws `ShikiUsageError` in development (in production, `setValue` buffers with the current pass; `reset` and `submit` diagnostics are development-only).

Use the draft handle (`d.x.$value = …`) inside `reaction`, and move async requests or `reset` / `submit` actions to `watch` (writing async results back with `form.setValue` or `form.batch`).

## Bare property writes and misspelled `$` states

```ts
// ✗ Missing `$`
d.user.name.value = 'Ada'

// ✗ Misspelled state name
d.user.name.$valeu = 'Ada'
const v = d.user.name.$valeu
```

- Assigning a non-`$` property on a handle throws `ShikiUsageError` in development and is ignored in production (without throwing a native `TypeError`).
- Reading or writing a missing near-spelling of a reserved `$` state throws `ShikiUsageError` in development; in production, reads return `undefined` (never a truthy child handle) and writes are ignored. Existing non-reserved own data keys starting with `$` (like `$values`) still resolve as normal child fields.
